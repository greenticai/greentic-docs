This page lists the kinds of infrastructure that an extension can ask the platform to host, what
runs inside each hosted instance, and how far each one has got. The model is in
[Hosted Infrastructure](/concepts/hosted-infrastructure/). The declaration format is in
[Infrastructure Resources for Extensions](/extensions/infrastructure-resources/). Where
instances run is set up in [Hosting Targets](/admin/hosting-targets/).

<Aside type="note" title="Status and roadmap (12 November 2026)">
**Live today**
- Managed **Qdrant**, **Redis** and **RabbitMQ** on an AWS ECS Fargate hosting target, with data on EFS.
- Redis is hosted as a REST gateway plus a Redis server in one task (`greentic.redis` 0.1.3 is published).
- RabbitMQ is hosted as the official image with its management API (`greentic.rabbitmq` 0.1.2 is published).
- Hosting targets as a platform setting with a Check button, the image policy `any`, custom CPU and memory per resource with per-target ceilings, and deletion that removes the instance, its data, its secret and its load balancer rule.

**Merged, but not published and not available**
- **MongoDB** (RESTHeart gateway plus MongoDB Community). The `greentic.mongodb` 0.1.2 declaration is merged in the extension repository, but the Store lists only 0.1.1, which has no hosting declaration. The declaration also uses `auth.template`, which an admin release has to add.
- **PostgreSQL and MySQL** through the read-only SQL gateway. The gateway is merged in the `greentic.sql` repository. The Store lists `greentic.sql` 1.4.1, which has no hosting declaration, and the declaration in the repository is a draft.

**In development, not available**
- Provider logic that runs inside extensions (provisioning written as extension code instead of a declaration).
- Kubernetes hosting beyond a private ClusterIP service. That has been proven only on a local kind cluster. None of the kinds below has been run on a real Kubernetes cluster.
</Aside>

## What every hosted instance has in common

- **One instance per resource.** Each resource gets its own task (AWS) or pod, with its own key. Nothing is shared between workspaces.
- **One public port.** Only the container the load balancer targets is reachable, over https at `https://h-<id>.<dns domain>` on port 443. The database or broker behind it listens on the loopback address of the same task and has no exposed port.
- **A generated key.** The platform generates one secret per instance, stores it in a secret store and injects it into the container. The extension reads it as the `credential` of the staged connection. The workspace sees "Connection: set" and never the value. Whoever holds the key owns the whole dedicated instance.
- **Data on EFS.** One container per task mounts an EFS access point for its data path, so data survives a task restart or replacement. Deleting the resource deletes the data.
- **Isolation by instance.** A hosted connection carries `isolation: dedicated` in its `extras`, so the extension uses no key or collection prefix.
- **Sizes.** The default is the `small` class (512 CPU units and 1024 MiB), unless the declaration sets another size. You can set a custom size per resource within the target's ceiling. See [Custom CPU and memory](/extensions/infrastructure-resources/#custom-cpu-and-memory-per-resource).
- **Cost.** Each instance is a Fargate task that runs around the clock plus an EFS access point. This is not metered yet.

## The catalog

| Kind | Extension | Status | What runs | Port the load balancer targets | Default size |
|---|---|---|---|---|---|
| `vector-store/qdrant` | `greentic.rag-qdrant` 0.6.5 | Live | Qdrant | 6333 | 512 / 1024 MiB (`small`) |
| `cache/redis` | `greentic.redis` 0.1.3 | Live | REST gateway and Redis | 8079 | 512 / 1024 MiB (`small`) |
| `queue/rabbitmq` | `greentic.rabbitmq` 0.1.2 | Live | RabbitMQ with the management plugin | 15672 | 512 / 1024 MiB |
| `database/mongodb` | `greentic.mongodb` 0.1.2 | Merged, not published | RESTHeart and MongoDB Community | 8080 | 1024 / 2048 MiB |
| `database/postgres` | `greentic.sql` | Merged gateway, hosting not published | SQL gateway and PostgreSQL | 8080 | Draft: 512 / 1024 MiB |
| `database/mysql` | `greentic.sql` | Merged gateway, hosting not published | SQL gateway and MySQL | 8080 | Draft: 1024 / 2048 MiB |

Sizes are CPU units (1024 is one vCPU) and MiB of memory. An extension can declare larger or
smaller sizes. A custom size on the resource replaces both.

### Qdrant (`vector-store/qdrant`) — live

- **What runs.** The `qdrant/qdrant` image as a single container. Qdrant is the service itself, so there is no separate gateway.
- **Authentication.** The generated key is Qdrant's API key (`QDRANT__SERVICE__API_KEY`). Clients send it in the `api-key` header.
- **Data.** `/qdrant/storage` on EFS. Snapshots are written under the same path.
- **Health check.** `/healthz`.
- **Owned by.** The declaration lives in the `greentic.rag-qdrant` extension. The admin also keeps a built-in Qdrant spec as a fallback, so Qdrant works even when no extension declares it.

### Redis (`cache/redis`) — live

- **What runs.** Two containers in one task. The primary is a Redis REST gateway (`hiett/serverless-redis-http`, the Upstash REST protocol) on port 8079, behind the load balancer. The sidecar is stock Redis, bound to the loopback address of the task. Both images are pinned by digest.
- **Why a gateway.** An extension has no TCP, so it cannot speak the Redis protocol. It talks https to the gateway, which forwards to Redis on `127.0.0.1:6379`.
- **Authentication.** The generated key is the gateway's bearer token (`SRH_TOKEN`). Redis itself has no password. Only the gateway port is open in the security group, and Redis refuses non-loopback clients when no password is set. The token holder can run any Redis command on this dedicated instance, although the `redis_*` tools expose no flush or raw command.
- **Data.** `/data` on EFS, mounted in the Redis container. Redis runs with its image defaults: periodic snapshots to the data directory and a save on a clean shutdown, no append-only file. A crash can lose the writes since the last snapshot.
- **Health check.** The gateway answers `/`. The Redis container is checked with `redis-cli ping` and starts before the gateway.
- **Owned by.** The gateway image, the Redis image and the wiring are all declared by `greentic.redis`. The admin runs them without knowing what Redis is.

### RabbitMQ (`queue/rabbitmq`) — live

- **What runs.** The official `rabbitmq:3.13.7-management` image as a single container. The management plugin is part of the image. The extension talks to the management API on port 15672, not to AMQP. The AMQP port (5672) is never opened.
- **Authentication.** The user is `greentic`, a literal in the declaration and also published to the extension as the `username` extra. The generated key is the password (`RABBITMQ_DEFAULT_PASS`) and is also the connection's `credential`.
- **Virtual host.** The image creates the vhost `greentic` at first start and gives the user full permissions on it. The default vhost `/` is not created.
- **Data.** `/var/lib/rabbitmq` on EFS. The node name is pinned to `rabbit@localhost`, because the default name contains the container host name, which changes on every Fargate task, and a replaced task would otherwise start on an empty data directory.
- **Health check.** `/` on the management listener answers 200 without credentials. `/api/*` answers 401.
- **Queues.** The hosted broker starts empty. Queues still have to be created on it.
- **Owned by.** `greentic.rabbitmq` declares everything.

### MongoDB (`database/mongodb`) — merged, not published

- **What is merged.** `greentic.mongodb` 0.1.2 in its repository declares hosting. The Store lists only 0.1.1.
- **What it would run.** Two containers. The primary is RESTHeart Community (`softinstigate/restheart`) on port 8080, behind the load balancer. The sidecar is MongoDB Community (`mongo`), started with `--bind_ip 127.0.0.1`, no exposed port and no authentication of its own. Both are pinned by digest.
- **Authentication.** RESTHeart's default `admin` account is disabled. The platform renders a configuration value (`RHO`) in which one user, `gw`, has the generated key as its password, and injects it from the secret store. The connection carries `extras.auth = basic` and `extras.user = gw` with the bare key as the credential. This needs the `auth.template` field, described in [the declaration reference](/extensions/infrastructure-resources/#authtemplate-render-the-key-into-a-configuration-value). **A released admin does not support `auth.template` yet**, so the declaration is refused until the admin is released.
- **Data.** `/data/db` on EFS, mounted in the MongoDB container.
- **Health check.** RESTHeart answers `/ping`. It reports liveness only. The MongoDB container is checked with `mongosh`.
- **Collections.** The extension creates a collection on the first insert into it (`PUT`, then a retry), because RESTHeart answers 404 for a `POST` into a missing one.
- **Licences.** RESTHeart is AGPL-3.0 and MongoDB Server is SSPL-1.0. Review them before you admit these images.

### PostgreSQL and MySQL (`database/postgres`, `database/mysql`) — gateway merged, hosting not published

- **What is merged.** The read-only SQL gateway (`greentic-sql-gateway`) is merged in the `greentic.sql` repository. It implements `GET /schema` and `POST /query`, which are exactly what the extension calls. The Store lists `greentic.sql` 1.4.1, which has no hosting declaration, and the hosting declaration in the repository is a draft, not part of the extension's `describe.json`.
- **What it would run.** The gateway on port 8080 behind the load balancer, with PostgreSQL 17 or MySQL 8.4 as a sidecar on the loopback address of the task.
- **Authentication.** The generated key is the gateway's bearer token. The gateway creates a read-only database role at start and queries only as that role.
- **Safety.** Only one `SELECT` or `WITH ... SELECT` statement is accepted. Each query runs in a read-only transaction with a time limit, a row cap (1000 by default) and a response size cap. The gateway is a read path: the extension cannot write to a hosted database.
- **Data.** The database data directory on EFS. Running PostgreSQL or MySQL on EFS has been checked on local disk only, not on EFS. Expect slower writes. MySQL needs at least 1 GiB of memory.
- **Licences.** MySQL is GPL-2.0. PostgreSQL uses the PostgreSQL licence.

## What each party owns

| | Qdrant | Redis | RabbitMQ | MongoDB | PostgreSQL / MySQL |
|---|---|---|---|---|---|
| Declares images, ports, env, data path, sizes | `greentic.rag-qdrant` | `greentic.redis` | `greentic.rabbitmq` | `greentic.mongodb` | `greentic.sql` (draft) |
| Builds and maintains the gateway image | Not needed | Upstream open-source image | Not needed | Upstream open-source image | The `greentic.sql` repository |
| Generates and injects the key | Admin | Admin | Admin | Admin | Admin |
| Runs the instance, the load balancer rule, EFS and cleanup | Admin | Admin | Admin | Admin | Admin |
| Reads the connection at run time | Extension | Extension | Extension | Extension | Extension |

The gateway image for a kind belongs to the extension's repository, never to the admin. The admin
holds no knowledge of Redis, MongoDB or SQL. It runs whatever a trusted declaration says.

## Operator checklist

Before the first hosted resource of any kind:

1. **Add a hosting target** of kind `aws_ecs` and press **Check**. Every step must pass. See [Hosting Targets](/admin/hosting-targets/).
2. **Grant the admin's role the hosting permissions**, including `ecs:DescribeClusters`, which is part of the read permissions. Give the task execution role access to the per-resource secrets (`greentic/infra/*`), EFS and the log group. Set `GREENTIC_INFRA_ADMIN_PRINCIPAL_ARN` so Check can simulate the permissions.
3. **Open one security group rule per kind port.** The platform writes no EC2 rules. For each kind you intend to host, the shared task security group must allow that kind's port from the load balancer's security group only: 6333 for Qdrant, 8079 for Redis, 15672 for RabbitMQ, and 8080 for MongoDB, PostgreSQL and MySQL once they are available. A missing rule shows as failed health checks. This will be automated later.
4. **Set up wildcard DNS and a certificate.** `*.<dns domain>` must point at the load balancer, and the https listener needs a publicly trusted certificate. The admin has no Route 53 permissions.
5. **Check the image policy.** The default `any` admits every valid repository that a platform-published extension declares. Switch to `allowlist` if you want to name the repositories yourself, and add the repositories of the kinds you intend to host.
6. **Set the size ceiling** (`maxCpu`, `maxMemoryMib`) on the target if the default of 4096 CPU units and 16384 MiB is not what you want.
7. **Install the extension version that declares hosting**: `greentic.redis` 0.1.3 or later, `greentic.rabbitmq` 0.1.2 or later, `greentic.rag-qdrant` 0.6.5 or later.
