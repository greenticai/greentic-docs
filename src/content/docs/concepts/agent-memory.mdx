An [agentic worker](/concepts/agentic-workers/) can remember things across turns and across
sessions. Memory has **two tiers**, configured in the optional `memory` block of the worker's
`AgentConfig`:

| Tier | Scope | Backing | Runner requirement |
|------|-------|---------|--------------------|
| **Short-term** (working memory) | Within a conversation | In-memory provider | Built in; needs a state store to run the worker at all |
| **Long-term** | Across conversations | Chronicle (persistent) | `long-term-chronicle` feature + `GREENTIC_CHRONICLE_*` |

```jsonc
// AgentConfig.memory
"memory": {
  "short_term": { "enabled": true },
  "long_term":  { "provider": "chronicle", "credential_ref": "chronicle-main" }
}
```

## Short-term (working) memory

Short-term memory is the worker's scratchpad within a conversation. It is served by an
always-on in-memory provider, so nothing extra is needed to build it — the model gets
`remember` / `recall` behaviour when `memory.short_term` is enabled.

<Aside type="caution" title="Where the conversation state lives">
Short-term working memory is separate from the **conversation state store** that lets a
`dw.agent` node run. The runner picks that store with `GREENTIC_AW_STATE_BACKEND`
(`redis`, `memory` or `disk`). With nothing set it uses `redis` when `GREENTIC_AW_REDIS_URL` is
present and otherwise `memory`. The `memory` backend lives in the process, so it is lost when
the worker restarts or scales to zero. Use `redis` (with `GREENTIC_AW_REDIS_URL`) or `disk`
(with `GREENTIC_AW_STATE_PATH`) when a conversation must survive that.
</Aside>

## How much of the conversation a worker keeps

A worker does not hand the whole conversation to the model for ever. At the end of every turn
the runtime trims the conversation to a **history window**, and that trimmed conversation is
what the model sees on the next turn. The window is counted in **messages** — yours, the
worker's and tool results. System messages are not counted and are never dropped. (The
setting is named `max_history_turns`, but it counts messages, not exchanges.)

| Preset | History window | Also |
|--------|----------------|------|
| **Light** | 10 messages | 4 rounds of thinking and tool calls, 30 seconds per turn |
| **Standard** (default, and a worker with no preset) | 20 messages | 8 rounds, 60 seconds |
| **Heavy** | 40 messages | 20 rounds, 180 seconds |

To change only the window, set **Conversation history (messages)** in the composer's **Limits**
tab (`limits.max_history_turns`). It accepts 1 to 100 and leaves the preset's other limits
alone. Leave it empty to use the preset's window; a value outside the range is clamped, not
rejected. The empty field shows the window the chosen preset gives.

### Summarise older history

By default the messages that fall out of the window are simply dropped. Switch on **Summarise
older history** (`limits.compact_history`, off by default) and they are folded into one note
instead, kept before the conversation and updated each time more falls out. The worker then
still knows what the first messages said, in compressed form.

<Aside type="caution" title="It costs a model call">
Summarising uses **one extra model call every time the window overflows**, which in a long
conversation is every turn. If that call fails the older messages are dropped, as if the
setting were off. A runtime built before this setting existed ignores it without an error
and drops the oldest messages.
</Aside>

### In a flow

The **Agentic Worker** (`dw.agent`) node has the same two settings as per-node overrides,
**Conversation history (messages)** (`max_history_turns`) and **Summarise older history**
(`compact_history`). Leave them unset to use the worker's own. A worker bound by several nodes
in one flow must use the same value in each.

The window only shapes what is kept. Where the conversation is kept, and whether it survives a
restart, is the state store described above.

## Long-term memory

Long-term memory persists facts **across** conversations, backed by
[Chronicle](https://github.com/greenticai) (embedded SurrealDB by default, or an external
graph store). Before each turn the worker can surface relevant long-term facts and inject
them into the prompt.

Long-term memory is **opt-in at the runner build**: the runner must be built with the
`long-term-chronicle` feature, and the tier stays silently disabled unless the Chronicle
environment is configured. It never fails worker startup — an unconfigured tier is simply
inactive.

<Aside type="note" title="Feature-gated runner build — gtc 1.1.2">
The default deployed runner ships with features `verify` + `agentic-worker` only, so
long-term memory is **not** active on a stock build. `gtc 1.1.2` adds a knowledge/memory-
enabled runner artifact (`runner-full`, built with `long-term-chronicle` +
`knowledge-chronicle`) plus `gtc start` / `gtc doctor` checks that warn when a worker
declares memory but the running binary or environment can't serve it.
</Aside>

## Reference

| Variable | Purpose |
|----------|---------|
| `GREENTIC_AW_STATE_BACKEND` | Conversation state store: `redis`, `memory` or `disk`. Default: `redis` if `GREENTIC_AW_REDIS_URL` is set, else `memory`. |
| `GREENTIC_AW_REDIS_URL` | Redis URL for the `redis` backend. `redis` selected with no URL disables `dw.agent` nodes. |
| `GREENTIC_AW_STATE_PATH` | File used by the `disk` backend. |
| `GREENTIC_CHRONICLE_*` | Long-term memory (Chronicle) connection. Absent → long-term tier inactive. |

<Aside type="tip" title="Authoring">
Configure both tiers visually in the Designer composer's **Memory** section, or (from
`gtc 1.1.2`) declare them in a [`WorkerSpec`](/concepts/agent-types/#authoring) `memory`
block and build with `gtc worker build`.
</Aside>
