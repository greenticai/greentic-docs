A **hosting target** is a place where the platform runs hosted infrastructure for extensions, for
example a dedicated Qdrant instance. A platform admin adds targets as a platform setting. Several
targets can be live at once. Every hosted resource keeps the target it was created on.

What to run, and with which sizes and environment, comes from the extension's `hosting`
declaration. The admin only deploys and connects. See
[Hosted Infrastructure](/concepts/hosted-infrastructure/).

<Aside type="note" title="Status and roadmap (12 November 2026)">
**Live today**
- Hosting targets as a platform setting: add, edit, enable, set a default, **Check**, and import from the current deployment.
- The image policy `any` (the default) and `allowlist`.
- Managed **Qdrant**, **Redis** and **RabbitMQ** on AWS ECS Fargate with EFS storage, https through the shared load balancer, a per-resource key, admin log lines and CloudWatch container logs.
- Custom CPU and memory per resource, with a per-target ceiling (`maxCpu`, `maxMemoryMib`).
- Deleting a hosted resource removes the service, task definitions, target group, load balancer rule, EFS access point and secret.

**Merged, but not published and not available**
- Hosting for **MongoDB**. Its extension declaration needs `auth.template`, which no released admin supports yet.
- Hosting for **PostgreSQL and MySQL** through the SQL gateway. The Store has no `greentic.sql` version that declares hosting.

**In development, not available**
- Applying the Kubernetes `storageClass`, `publicHostDomain` and `ingressClass` settings. They are stored and validated, but the Kubernetes adapter still creates a private ClusterIP service on the default storage class.
- Kubernetes hosting beyond that, proven only on a local kind cluster. A real Kubernetes cluster target has not been run.
- Other target kinds (GCP, VM), and provisioning logic running inside extensions.
- Automatic security group rules for the port of each hosted kind. Today you open them yourself.
</Aside>

Only a platform admin can manage hosting targets. Every change is audited.

## Target kinds and fields

### AWS ECS

Runs each instance as an ECS Fargate service with its data on EFS. The admin uses its own AWS
identity; no credential is stored in the target.

| Field | Meaning |
|---|---|
| `region` | AWS region. |
| `cluster` | ECS cluster. |
| `vpcId` | VPC. |
| `subnets` | List of subnets. |
| `securityGroup` | Shared security group. |
| `efsId` | EFS file system for instance data. |
| `executionRoleArn` | Execution role for the tasks. It must read the per-resource secrets (`greentic/infra/*`), mount EFS and write the log group. |
| `taskRoleArn` | Optional task role. |
| `listenerArn` | Optional https listener of the shared load balancer. |
| `certificateArn` | Optional certificate. |
| `dnsDomain` | Optional domain for instance hostnames (`*.<dns domain>`). |
| `installationId` | Identifies this admin installation. Every object created is tagged with it. |
| `logGroup` | Optional log group. Default `/ecs/greentic-infra-hosts`. |
| `maxCpu` | Optional. The largest custom CPU size (in CPU units, 1024 is one vCPU) a resource on this target may ask for. Default 4096. |
| `maxMemoryMib` | Optional. The largest custom memory size in MiB. Default 16384. |

The admin's AWS permissions are given to its role out of band, as an IAM policy with these parts:

- **Reads** (not limited by tag): `ecs:DescribeClusters`, `ecs:DescribeServices`, `ecs:DescribeTasks`, `ecs:DescribeTaskDefinition`, `ecs:ListServices`, `ecs:ListTasks`, `ecs:ListTaskDefinitions`, `ecs:ListTagsForResource`, the EFS and load balancer describe actions, `secretsmanager:DescribeSecret` and `GetSecretValue`, `ec2:DescribeSecurityGroups` and `ec2:DescribeNetworkInterfaces`.
- **Creates**, allowed only when the request carries both tags `greentic:infra=<installation id>` and `greentic:managed=true`: services, task definitions, EFS access points, target groups, listener rules and secrets. Tagging is allowed only as part of such a create.
- **Changes and deletes**, allowed only on objects that already carry both tags.
- **Secrets Manager tagging** is allowed on `greentic/infra/*` by name, without tag conditions, because that service does not honour the request-tag conditions.
- **`iam:PassRole`** for the execution role (and the task role when set), only to `ecs-tasks.amazonaws.com`.
- **No Route 53 and no EC2 write permissions.** The adapter writes no security group rules and no DNS records.

Every object the adapter creates is tagged with both tags. It changes or deletes only objects that
carry both. `ecs:RegisterTaskDefinition` and `ecs:DeregisterTaskDefinition` do not evaluate
resource tags in every region. If IAM refuses them under the condition, the Check lists them as
missing and you widen only those two actions.

### Kubernetes

| Field | Meaning |
|---|---|
| `namespace` | Namespace for instances. |
| `installationId` | Identifies this admin installation. |
| `storageClass` | Optional. Stored and validated, **not applied yet**. |
| `publicHostDomain` | Optional. Stored and validated, **not applied yet**. |
| `ingressClass` | Optional. Stored and validated, **not applied yet**. |
| `maxCpu`, `maxMemoryMib` | Optional size ceiling, same meaning and defaults as on ECS. |
| credential | Optional kubeconfig, sealed and never shown again. Without one the admin uses its in-cluster identity. |

The target view says that the three optional fields are not applied.

## Add a target

1. Open the hosting targets settings as a platform admin.
2. Choose the kind (`aws_ecs` or `kubernetes`), give it a name (1 to 64 characters of `a-z`, `0-9`, `-`, unique) and fill in the fields above.
3. Save. The target starts as `unchecked`.
4. Press **Check**.

You can also use the API: `GET` and `POST /api/admin/infra-resources/targets`,
`PUT` and `DELETE /api/admin/infra-resources/targets/{id}`.
A change to a target resets its status to `unchecked`. The kind of a target never changes.

## The Check button

Check stores the result as `ready` or `invalid` with the time it ran, and shows each step.

- **AWS ECS:** the settings are valid, the cluster is active, the file system is readable, the
  listener is readable (when set), and an IAM simulation of the permissions the adapter needs.
  The simulation runs only when the admin knows its own role (`GREENTIC_INFRA_ADMIN_PRINCIPAL_ARN`).
  Otherwise Check reports that it was not evaluated.
- **Kubernetes:** the settings are valid, a client can be built, and the namespace is readable.

## Default target and enabling

- At most one target is the **default**. A disabled target cannot be the default.
- When you create a managed resource without naming a target, the platform uses the default
  enabled target if it can run that kind. A named target must exist, be enabled and have a usable
  adapter. Nothing falls back from an explicit choice.
- Disabling a target keeps serving the resources already on it. It only stops accepting new ones.
- Without any target, the older deploy-time configuration (`GREENTIC_INFRA_PROVISIONER`) keeps
  working unchanged.

## Import from the current deployment

If the platform already runs hosted instances from deploy-time `GREENTIC_INFRA_*` settings, use
**Import from the current deployment** to build a target from them. It answers
`409 infra_target_env_not_configured` when there is nothing to import.

## Image policy

The image policy decides which container repositories a hosting declaration may use. It is a
platform admin setting and every change is audited.

| Policy | Meaning |
|---|---|
| `any` (default) | Every syntactically valid repository is admitted. |
| `allowlist` | Only the listed repository prefixes. An entry matches itself and anything nested under it, so `qdrant/qdrant` does not match `qdrant/qdrant-evil`. An empty stored list falls back to `GREENTIC_INFRA_HOST_IMAGE_ALLOW`, whose initial value is `qdrant/qdrant`. An allow-list must name every repository of a kind: for example Redis uses a gateway repository and a Redis repository. |

**What this means for security.** In `any` mode the platform runs an image chosen by an extension
that the platform published. Even then it still requires a pinned tag or digest (never `latest`),
refuses unknown fields and secrets in `env`, and refuses reserved variable names and a root user.
Only a platform-owned, published extension can supply a spec. Use `allowlist` if you want to
decide yourself which repositories may run in your account. A change takes effect on the next read
with no restart. A fresh install no longer allows only `qdrant/qdrant`.

## Deleting a resource and a target

- **Deleting a hosted resource destroys the instance and its data.** For AWS this removes the
  service, task definitions, target group, load balancer rule, EFS access point and secret. There
  is no undo.
- **Deleting a target** is refused with `409 infra_target_in_use` while resources or parked
  clean-up items still name it.

## Where the logs are

- **Admin log.** Each AWS step writes an `infra host:` line with the host id, the AWS action, the
  AWS error code and a truncated message. Request bodies and secret values are never logged.
- **Container logs.** CloudWatch log group `/ecs/greentic-infra-hosts` (or your `logGroup`), with
  the host id as the stream prefix. This is where you see why a container did not start.
- **What the console shows.** The admin API and console show a fixed phrase only. The detail is in
  the two places above.

The execution role needs `logs:CreateLogStream` and `logs:PutLogEvents` on the group, and
`logs:CreateLogGroup` unless you create the group yourself.

## Size ceiling

`maxCpu` and `maxMemoryMib` set the largest custom size a resource on the target may ask for. When
they are empty the ceiling is **4096 CPU units (4 vCPU) and 16384 MiB (16 GiB)**.

That default is a valid Fargate pair. It is twice the `large` class on CPU and four times on
memory, and it stops short of the 8 and 16 vCPU Fargate tiers, which cost two and four times as
much, so a custom size cannot reach them by accident. If you want those tiers, raise the ceiling on
the target. On ECS the ceiling cannot exceed Fargate's largest pair (16384 CPU units and 122880
MiB).

The ceiling is checked when a resource is created, when it is resized, and again by the periodic
reconcile. A resource whose size is above its target's current ceiling fails with a fixed message
and nothing is created or changed. How to set a custom size is in
[Infrastructure Resources for Extensions](/extensions/infrastructure-resources/#custom-cpu-and-memory-per-resource).

## What stays with the operator on AWS

The platform does not create these. You maintain them:

- **One security group rule per hosted kind.** The shared task security group must allow the port that kind's load-balanced container listens on, from the load balancer's security group only. A port that is not open fails health checks. The platform does not write EC2 rules yet.

  | Kind | Port |
  |---|---|
  | `vector-store/qdrant` | 6333 |
  | `cache/redis` (the REST gateway) | 8079 |
  | `queue/rabbitmq` (the management API) | 15672 |
  | `database/mongodb`, `database/postgres`, `database/mysql` (gateways, when available) | 8080 |

  Never open the ports of the services behind a gateway: Redis 6379, AMQP 5672, MongoDB 27017, PostgreSQL 5432 or MySQL 3306.
- **Wildcard DNS**: `*.<dns domain>` pointing at the load balancer. The admin has no Route 53 permissions.
- **A publicly trusted certificate** on the https listener (ACM). A proxied provider such as Cloudflare in front of the load balancer also works. Without a certificate the load balancer serves http only.
- **The shared security group, the listener, the execution role and the EFS file system.**

Each hosted instance is one Fargate task running around the clock plus an EFS access point. This
is not metered yet.

### Checklist before you host a new kind

1. The hosting target shows **ready** after **Check**, and the IAM simulation step was evaluated, not skipped.
2. The security group allows the kind's port from the load balancer group (table above).
3. `*.<dns domain>` resolves to the load balancer and the listener has a trusted certificate.
4. The image policy admits the repositories the kind uses: automatic with `any`, or add them to the allow-list.
5. The extension version that declares hosting is installed from the Store.
6. The size ceiling suits the sizes the kind and your tenants will use.

See [Hosted Kinds Catalog](/extensions/hosted-kinds-catalog/) for the port, size and storage of each kind.
