# Azure Credentials

An `azure` deploy environment deploys your workers to **Azure Container Apps**
in your own subscription. The Designer builds the worker bundle, pushes it to
your Azure Container Registry (ACR), and creates the Container App.

Two things have to exist before the first deploy: a small set of Azure
resources that **you** create, and an **ARM service principal** the deploy signs
in with. All the identifiers involved are GUIDs, they look alike, and putting
one in the wrong box produces an authentication error that names none of them —
so this page is also about telling them apart.

<Aside type="note">
The deploy does **not** create the resource group, the Container Apps
environment, the registry or the Log Analytics workspace. They are yours; the
deploy only creates and updates Container Apps inside them.
</Aside>

## What you create first

| Resource | Notes |
| --- | --- |
| Resource group | Holds everything below. Putting it all in one group makes cleanup a single `az group delete`. |
| Azure Container Registry | Basic is enough. Its **login server** (for example `myregistry.azurecr.io`) is a field below. |
| Log Analytics workspace | Optional for deploying, needed to read logs. |
| Container Apps environment | Must be **public**. A VNet-internal environment is refused. |

The subscription must have the `Microsoft.App`, `Microsoft.ContainerRegistry`
and `Microsoft.OperationalInsights` resource providers registered.

## The fields

The environment form asks for the values that say *where* to deploy, and for the
service principal that deploys.

| Field | What it is |
| --- | --- |
| Region | the Azure location of your Container Apps environment, for example `southeastasia` |
| Subscription ID | the **billing container** the resources live in |
| Entra tenant ID | your **Entra ID directory** |
| Resource group | the existing group that holds the environment |
| Container Apps environment | the **name** of the existing environment |
| ACR login server | for example `myregistry.azurecr.io` |
| Log Analytics workspace ID | optional; the workspace's customer ID (a GUID), needed for the log tab |
| Tenant ID, Client ID, Client secret, Subscription ID | the service principal (below) |

The deploy reads the non-secret values from this form, so a resource group or
environment name you type here is what it deploys into. If a deploy answers that
a setting "is required and is not set", the value is missing from this form.

<Aside type="tip">
The single commonest credential mistake is pasting the client secret's **Secret
ID** — which *is* a GUID, and sits next to the value in the portal — instead of
the secret **Value**. If your secret looks like a GUID, you copied the wrong
column.
</Aside>

## Creating the service principal

Give the principal only what the deploy calls. A custom role scoped to the
resource group is enough; `Contributor` also works but is broader than needed.

<Steps>

1. **Create a role limited to the deploy's calls**, scoped to the resource group:

   ```json
   {
     "Name": "Greentic ACA Deployer (my-rg)",
     "Description": "Deploys Greentic workers to Azure Container Apps",
     "Actions": [
       "Microsoft.App/containerApps/read",
       "Microsoft.App/containerApps/write",
       "Microsoft.App/containerApps/delete",
       "Microsoft.App/containerApps/listSecrets/action",
       "Microsoft.App/containerApps/revisions/read",
       "Microsoft.App/containerApps/revisions/activate/action",
       "Microsoft.App/containerApps/revisions/deactivate/action",
       "Microsoft.App/containerApps/revisions/restart/action",
       "Microsoft.App/managedEnvironments/read",
       "Microsoft.App/managedEnvironments/join/action",
       "Microsoft.App/operations/read",
       "Microsoft.Authorization/permissions/read"
     ],
     "NotActions": [],
     "AssignableScopes": ["/subscriptions/<subscription-id>/resourceGroups/my-rg"]
   }
   ```

   ```bash
   az role definition create --role-definition role.json
   ```

   `managedEnvironments/join/action` is easy to miss: creating a Container App
   that references an environment is refused without it, even if
   `containerApps/write` is granted.

2. **Create the service principal** with that role:

   ```bash
   az ad sp create-for-rbac \
     --name greentic-aca-my-rg \
     --role "Greentic ACA Deployer (my-rg)" \
     --scopes /subscriptions/<subscription-id>/resourceGroups/my-rg
   ```

   It prints `appId`, `password` and `tenant`. `password` is shown once.

3. **Let it push bundles** to the registry, and optionally read logs:

   ```bash
   az role assignment create --assignee <appId> --role AcrPush \
     --scope $(az acr show -n <registry> --query id -o tsv)

   az role assignment create --assignee <appId> --role "Log Analytics Reader" \
     --scope $(az monitor log-analytics workspace show -g my-rg -n <workspace> --query id -o tsv)
   ```

</Steps>

Map the output to the form:

| Output | Field |
| --- | --- |
| `appId` | Client ID |
| `password` | Client secret |
| `tenant` | Tenant ID |
| your subscription | Subscription ID |

Your subscription ID, if you do not have it to hand:

```bash
az account show --query id --output tsv
```

## How the worker pulls its bundle

By default the worker pulls its bundle from your registry with the **same
service principal** that pushed it (`AcrPush` includes pull). The deploy report
says so in its `registry-credential` step.

To give the worker read-only access instead, create a repository-scoped ACR
token and save it as the environment's pull token. The pull token is not a
field of the admin console form today; it is set through the Designer's Azure
Container Apps settings.

```bash
az acr scope-map create -r <registry> -n greentic-pull \
  --repository 'greentic/*' content/read
az acr token create -r <registry> -n greentic-pull-token --scope-map greentic-pull
```

## Checking a deploy

A deploy ends in the unit's address. To confirm the worker is up, open
`https://<address>/healthz`; it answers `ok` once the revision is running. A
Container App is scaled to zero when idle, so the first request after a quiet
period can take longer.

Common failures and what they mean:

| Message | Cause |
| --- | --- |
| A setting "is required and is not set" | the resource group, environment name or ACR login server is missing from the environment form |
| `Not authorized` pulling the bundle | the registry login the deploy used cannot read the repository; check the service principal's `AcrPush` assignment or the saved pull token |
| `LinkedAuthorizationFailed` | the role is missing `Microsoft.App/managedEnvironments/join/action` |
| the environment is "internal" | the Container Apps environment is VNet-internal; the deploy needs a public one |

## What is not supported yet

- **Deleting an environment that has deployed units** is refused for Azure. Remove the Container
  Apps (or the resource group) in Azure yourself.
- **Azure OIDC / workload identity federation** is not offered by the form; it
  collects the client-secret style only.

## Rotating

Secrets expire — Azure caps a client secret's lifetime, and an expired secret
fails with the same unhelpful error as a wrong one. Add the new secret before
removing the old:

```bash
az ad app credential reset --id <appId> --append
```

Then update the environment and delete the superseded credential.

## Cleaning up

Everything above lives in one resource group, so removing it removes the
registry, workspace, environment and Container Apps. The service principal and
the custom role live outside the group:

```bash
az group delete -n my-rg --yes
az ad app delete --id <appId>
az role definition delete --name "Greentic ACA Deployer (my-rg)"
```

Delete the role after the group is gone; while a role assignment still exists
Azure refuses to delete it.
