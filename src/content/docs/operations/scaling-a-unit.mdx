title: Scaling a Unit Out
description: Run a deployed unit on more than one pod or instance behind a shared Redis, from the Designer's environment canvas, and what you must provide first
---

import { Aside } from '@astrojs/starlight/components';

By default a deployed unit runs as a single copy: one Kubernetes pod, or at most one Cloud Run
instance. That is deliberate. The runtime keeps its trigger state, conversation state and revision
pins in the memory of that one process, so a second copy would not see what the first one knows.

You can scale a unit out when you give the environment a **shared Redis**. The runtime then keeps
that state in Redis, and every pod or instance reads and writes the same data.

| Target | Setting | Needs |
|---|---|---|
| Kubernetes | Number of replicas (1 to 20) | A Redis URL |
| Cloud Run | Maximum instances | A Redis URL **and** a VPC connector |

## Before you start

- **A Redis you run.** Greentic does not provision one. It must be reachable from the pods or from
  the Cloud Run VPC, and the URL must start with `redis://`.
- **A deployer that supports it.** The control only appears when the deployer reports that it
  accepts scale-out settings. If you do not see it, the environment is on an older deployer and
  every deploy stays at one copy.
- **Workspace admin rights.** Only a workspace admin can change the setting.

## Set it up in the Designer

1. Open the environment on the canvas and go to the cloud target panel.
2. In the **Scale out** section, set the number of replicas (Kubernetes) or the maximum instances
   (Cloud Run).
3. Enter the Redis URL. On Cloud Run, also enter the VPC connector.
4. Save, then deploy the whole environment.

The Redis URL is stored sealed. The Designer never shows it again after you save it; the panel only
tells you that one is set.

<Aside type="note">
A **never-deployed Cloud Run environment shows no Scale out control**, because the deployer's
capabilities are read from the environment's store. Deploy once as a single copy, then scale out.
</Aside>

## What a deploy does

- With a value above 1 and a readable Redis, the deploy sends the scale-out settings and the
  runtime starts using Redis for its shared state. A green `scale-out` step in the deploy report
  confirms it.
- With a value of 1, nothing is sent and the deploy is exactly what it was before.
- If the deployer does not report the capability, the settings are not sent, and the `scale-out`
  step says it was skipped and why.

### When a deploy is refused

The deploy stops before anything is built if the settings cannot work:

| Message | Cause |
|---|---|
| Redis required | More than one replica or instance, but no Redis URL is set or it cannot be read |
| VPC connector required | Cloud Run above one instance, without a VPC connector |

Fix the setting and deploy again.

## Unit-scoped and staged deploys

A deploy of one unit, or a staged rollout, does not change the scale-out settings of the other
units.

- On **Cloud Run**, it re-sends the settings recorded by the last whole-environment deploy, so the
  units it re-ships keep the configuration they already run.
- On **Kubernetes**, it does not re-send the deployer's settings at all.

To change the scale-out settings, deploy the whole environment.

## Limits

- **A shared Redis is the only supported shared state.** If Redis becomes unreachable, the runtime
  fails loudly at startup rather than falling back to per-pod memory.
- **Secrets generated by each pod at boot are not shared.** The Designer already stages the WebChat
  signing key and the Webex webhook secret once for the whole environment, so those are the same
  across copies. Any other secret a pod invents for itself at boot is private to that pod.
- **Cloud Run uses a VPC connector.** Direct VPC egress (a network and subnet) is not exposed in the
  Designer.
- **Not yet exercised on a live cluster.** The behaviour is built and tested at the code level.
  Try a new setup on a non-critical environment first.
